# シミュレーションコア並列実行設計

## 1. 目的

本書は、MachiVerse のシミュレーションコアにおけるマルチスレッド実行の基本方針を定義します。

シミュレーションコアは超大規模な計算処理を担当するため、単一スレッドを前提とせず、複数スレッドを利用して計算処理を並列化できる構造とします。

## 2. 基本要件

- シミュレーションコアはマルチスレッド実行を前提とする。
- 実際に使用するworker budgetは、シミュレーションコアの外部Configから変更可能とする。
- Coreは標準受入profileとして少なくとも16 workerを実利用できる構造とし、16を実装上の固定上限にしない。
- Config schema 1.0の`runtime.worker-count`は`uint16 / 1..4096`とし、将来の32/64+ core hostでも同一production code pathを使用できるようにする。
- requested worker countがhost logical processor countを上回る指定もoperational oversubscriptionとして受理可能とし、必要に応じて警告する。ただしworld semanticsを変更したり、16へsilent clampしたりしない。
- マルチスレッド化によって30Hzの計算基準を満たせる構造を目標とする。
- 同一ワールドSeed、同一設定、同一操作列であれば、使用スレッド数や実際のスレッド実行順にかかわらず同一結果を得る。

## 3. 設定値の所有責任

スレッド数はシミュレーションコア自身の実行特性を決定する値であるため、シミュレーションコアが所有します。

ゲートウェイ、一般ビュー、管理ビューは、コアのスレッド数Configを直接参照しません。

スレッド数に関する設定例は次の通りです。

| 項目 | 所有者 | 基準・制約 |
|---|---|---|
| 使用スレッド数 | シミュレーションコア | 外部Configから設定 |
| worker budget上限 | シミュレーションコア | Config schema 1.0では4096。runtime内部に16固定上限を置かない |

Config keyは`runtime.worker-count`とし、Config schema 1.0では`OPERATIONAL / RUNTIME_SAFE`としてquiescent boundaryでatomic applyする。Config document formatその他の共通契約は`docs/design/phase4-config-specification.md`を正本とする。

## 4. 並列実行の責務境界

マルチスレッド化はシミュレーションコア内部の実装責務です。

ゲートウェイや各ビューは、コア内部で何スレッド使用されているかを前提として動作しません。また、コア・ゲートウェイ間プロトコルにも、内部スレッド構成への依存を持ち込みません。

これにより、コア内部の並列化方式を変更しても、他コンポーネントの実装変更を必要としない構造を維持します。

## 5. 30Hzとの関係

シミュレーションコアの計算頻度の基準値は30Hzです。

マルチスレッド化は、この30Hz計算を超大規模なシミュレーション処理で成立させるためのコア内部の実行手段として扱います。

1ステップ内はDomainだけでなく、Domain内の独立work itemもcanonical unitへ分割して並列化する。parallel computeの完了順はauthorityにせず、canonical reduce/commit barrierで決定的順序へ戻す。

以下の物理スケジューリング詳細は実装最適化として固定しない。

- すべての処理を毎ステップ並列実行するか
- スレッド間で処理を固定割当するか
- ワークスティーリング等を採用するか
- スレッドごとの担当領域を固定するか
- 同期ポイントをどこに置くか

## 6. 状態整合性

複数スレッドがシミュレーション状態を扱うため、並列実行によって状態整合性を破壊してはなりません。

詳細方式は未確定ですが、設計時には少なくとも以下を明示します。

- 各データの所有スレッドまたは更新責任
- 同一データへの同時書き込み可否
- 読み取りと書き込みの競合規則
- ステップ内の同期境界
- スレッド間通信または共有状態の扱い
- 更新順序がシミュレーション結果へ与える影響

## 7. 決定論と再現性

決定論的再現性は必須要件です。

同一ワールドSeed、同一設定、同一操作内容・適用順序・適用時点であれば、シミュレーション結果は必ず同一でなければなりません。

マルチスレッド化によって以下が変化しても、結果を変化させてはなりません。

- スレッドの実行開始順
- タスクの完了順
- OSスケジューラによる実行タイミング
- スレッド間の処理速度差
- 同一有効設定の下での内部並列実行タイミング

並列リダクション、競合解決、状態反映順序など、順序によって結果が変わり得る処理には決定的な順序規則または結果確定規則を設けます。

### 7.1 乱数との関係

シミュレーション結果へ影響するランダム要素は、ワールドSeedとワールド時間を基礎入力とする決定的ノイズから導出します。

共有PRNGの内部状態をスレッド間で順番に消費し、呼び出し順によって乱数結果が変化する方式を、シミュレーション結果決定の基準として使用しません。

同一ワールド時間に複数の抽選が必要な場合は、抽選対象や用途等を決定的に識別する追加入力が必要です。具体方式は別途定義します。

## 8. 性能上の原則

- スレッド数を増やすこと自体を目的としない。
- 同期・ロック・コンテキスト切り替えによるオーバーヘッドを考慮する。
- スレッド数ごとの処理時間を計測可能にする。
- 1、4、8、16 workerをcanonical acceptanceとして比較し、32、64以上でも同一実装を拡張利用できる構造とする。
- 外部Configの変更だけで使用スレッド数を調整できるようにする。
- 外部コンポーネントの負荷や接続数によってコア内部のスレッド構成が直接左右されないようにする。
- 性能最適化のために決定論的再現性を犠牲にしない。

## 9. 禁止事項

- 単一スレッドでのみ成立することを前提としたコア全体設計
- ゲートウェイやビューからコア内部のスレッドを直接制御すること
- 他コンポーネントのConfigからコアのスレッド数を直接変更すること
- プロトコルへ内部スレッドIDやスレッド実装詳細を公開契約として漏らすこと
- スレッド実行順やタスク完了順で世界状態が変化する実装
- 並列競合の勝敗を実行タイミング任せにすること
- 呼び出し順依存の共有乱数状態によってシミュレーション結果を決定すること

## 10. 今後決定が必要な事項

- 実行中のworker budget変更をどのquiescent boundaryで適用するか
- host topology / affinity / NUMAを将来どのoperational policyで扱うか
- 並列実行単位
- タスクスケジューリング方式
- データ分割方式
- 同期方式
- ロック戦略
- スレッドローカルデータの利用方針
- 並列処理時の例外処理
- 決定的な更新順序・競合確定規則
- 並列リダクションの決定論維持方式
- 決定的ノイズ関数・乱数変換方式
- 再現性検証方法
- 性能計測項目
