# Phase 4 QA-04 Gate4 Step2 determinism authority

Status: Complete candidate / normative amendment for `perf.reference.v1` Gate4 Step2  
Tracking: #240, #371, #372, #373, #374  
Parents: `phase4-performance-benchmark-profile.md`, `phase4-persistence-specification.md`, `phase4-core-snapshot-section-wire.md`

## 1. Purpose and scope

This amendment closes the normative gaps that block the Gate4 Step2 determinism matrix for the canonical QA-04 benchmark profile.

It defines, for `BenchmarkProfileId = perf.reference.v1` only:

1. a scalable durable representation of the profile-generated Operation lifecycle that preserves exact Operation semantics without materializing the full world-lifetime terminal catalog in every State digest;
2. the complete semantic payload of `transition.committed.v1` needed by recovery and determinism evidence;
3. durable promotion/defer decision authority for Detail transitions;
4. the four aggregate digests used with the existing final State digest by the 12-run determinism matrix;
5. the required 300-Step CrossDomainTransaction turnover binding.

This amendment does **not** weaken the ordinary external Operation contract. For worlds or Operations that are not covered by the closed canonical `perf.reference.v1` generator, the existing `operation_state` world-lifetime rules remain unchanged.

`releaseEvidenceCapable` remains false while Step2 evidence is being collected.

## 2. Canonical run and matrix

A Step2 evidence run MUST use the State numbering already fixed for Gate4:

- durable production basis: `State(1)`;
- 27,000 consecutive workload transitions;
- transition ordinal `t = 1..27,000` uses `injection_step=t-1`, executes from `State(t)`, and finalizes `State(t+1)`;
- final authority: `State(27001)`.

The matrix is exactly:

```text
worker_count = 1, 4, 8, 16
run_ordinal  = 1, 2, 3
```

All 12 runs MUST execute the same canonical input sequence. Worker count and run ordinal are diagnostic/execution settings and MUST NOT enter any semantic identity or digest defined here.

## 3. QA-04 generated Operation closed-set authority

### 3.1 Why a profile-specific authority is permitted

Every Operation admitted by the canonical `perf.reference.v1` run is generated by the already-canonical function:

```text
(profile_id, injection_step, family_token, family_ordinal)
  -> payload_digest
  -> OperationId
```

with `profile_id = perf.reference.v1` and the exact family distribution/load rules in the performance benchmark profile.

Therefore the complete Operation identity/payload input set for any closed prefix of injection Steps is reconstructible without storing one terminal `DurableOperationStateV1` row per generated Operation.

The compact authority below is valid **only** when all Operations in the covered range are produced by that generator. Any external/non-profile Operation forces the ordinary `operation_state` authority path.

### 3.2 Closed-prefix certificate

A canonical production run maintains `Qa04OperationClosedPrefixV1`:

```text
Qa04OperationClosedPrefixV1 {
  profile_id                 = "perf.reference.v1"
  first_injection_step       = 0
  last_closed_injection_step : uint64 | NONE
  terminal_operation_count   : uint64
  terminal_semantic_digest   : bytes32
}
```

`last_closed_injection_step = k` means every canonical Operation generated by `OperationsForStep(s)` for every `s in 0..k` has:

1. been durably admitted;
2. been durably scheduled for the canonical effective Step;
3. reached an ordinary terminal result in that effective Step;
4. been included in the terminal semantic accumulator defined below.

No hole is permitted. The prefix advances by exactly one injection Step after the corresponding transition COMMIT succeeds.

For `State(1)` the prefix is empty, `terminal_operation_count=0`, and the terminal accumulator has its genesis value.

### 3.3 Exact retry / dedup semantics

The closed-prefix certificate is a lossless semantic authority, not a probabilistic filter.

For a retry/query of an OperationId inside a closed prefix, Core MUST deterministically regenerate canonical descriptors for the covered generator coordinates until it finds the requested id. The implementation MAY maintain non-authoritative exact indexes/caches to accelerate lookup, but an index miss MUST NOT be interpreted as non-existence unless regeneration proves non-existence.

If regeneration discovers the same OperationId at more than one distinct canonical generator coordinate, or the same OperationId with a different immutable payload digest, the world fails closed with an identity-collision error. The collision MUST NOT be repaired by entropy, worker count, process identity, or arrival order.

This preserves world-lifetime retry/dedup semantics while allowing the normal no-retry benchmark path to avoid O(total historical Operations) work on every Step.

### 3.4 Current-Step materialization boundary

Only Operations that are not yet represented by the closed prefix need ordinary mutable lifecycle material during a Step.

For one workload transition the runtime MUST:

1. generate the exact canonical descriptor list for that injection Step;
2. validate OperationId uniqueness within that list;
3. bind each descriptor to the ordinary `StandardOperationV1` and `SameStepOrderKey` authority;
4. durably commit the admission/scheduling batch described below;
5. execute the ordinary domain/runtime path;
6. commit terminal outcomes atomically with `transition.committed.v1`;
7. advance the closed prefix only after that COMMIT succeeds.

After prefix advancement, terminal rows for that Step are no longer required in the mutable current-Step catalog because their exact semantic authority is the generator coordinate plus the committed prefix/terminal accumulator.

This is not deletion of semantic history: the terminal semantics remain recoverable from the generator and transition/history authorities.

## 4. Durable batch admission and scheduling

### 4.1 Transaction boundary

For `perf.reference.v1` generated Operations, the per-Operation requirement “durable before authoritative ACCEPTED/SCHEDULED” is satisfied by one SQLite transaction per lifecycle batch, not one SQLite transaction per Operation.

For a single injection Step, the admission/scheduling batch uses this exact canonical order:

```text
SameStepOrderKey ASC, then OperationId bytewise ASC
```

A batch transaction MUST atomically persist:

- the canonical injection Step;
- ordered OperationId + immutable payload digest + effective Step + SameStepOrderKey facts for every Operation in the batch;
- one normalized semantic batch digest;
- the batch cardinality;
- the history-chain record representing that batch.

The transaction commits before any item in that batch is treated as authoritatively scheduled.

Retrying the same batch after a failed/unknown COMMIT is idempotent: exact same semantic batch is accepted as the same authority; any mismatch fails closed.

### 4.2 History record

The profile-specific compact record type is:

```text
qa04.operation-batch.scheduled.v1
payload schema: qa04.operation-batch / 1.0
```

Normalized MV-DCBOR:

```text
map {
  0: "perf.reference.v1",
  1: injection_step uint64,
  2: effective_step uint64,
  3: array [
       array [
         operation_id bytes16,
         payload_digest bytes32,
         same_step_order_key bytes55
       ], ...
     ]
}
```

The array MUST already be in canonical scheduling order and MUST contain no duplicate OperationId.

The compact record is the authoritative history fact for generated admission/scheduling in the benchmark. It replaces per-item `operation.accepted.v1` and `operation.scheduled.v1` history records only for this closed generated set; ordinary Operations keep the standard record types.

### 4.3 State commitment

`perf.reference.v1` Step state MUST NOT recompute `DurableOperationSubstateV1.Canonicalize()` over all previously terminal generated Operations.

The Operation core authority for the QA-04 production run commits:

```text
map {
  0: mutable ordinary operation rows not covered by closed prefix,
  1: Qa04OperationClosedPrefixV1,
  2: active CrossDomainTransaction authority
}
```

under domain label:

```text
mv.qa04-operation-authority.v1
```

The mutable list uses the existing ordinary durable-operation canonicalization. The closed-prefix fields use the exact normalized structure from §3.2. CrossDomainTransaction authority uses the existing canonical transaction ordering/digest rules.

At the end of each canonical benchmark Step, all generated Operations for that Step are terminal; therefore the mutable generated-operation set is empty after COMMIT.

## 5. Snapshot and recovery binding

For the QA-04 production run, `core.operation-state` recovery material MUST carry enough information to reconstruct:

- the `Qa04OperationClosedPrefixV1` certificate;
- any mutable ordinary Operation rows not covered by the prefix;
- the existing CrossDomainTransaction authority.

Snapshot recovery MUST recompute the QA-04 Operation authority digest and reject any mismatch with the frozen `WorldStateV1.OperationState` reference.

A recovered closed prefix is accepted only if:

1. profile id is exactly `perf.reference.v1`;
2. `first_injection_step=0`;
3. the prefix endpoint is compatible with the snapshot State numbering;
4. `terminal_operation_count` equals the exact sum of `OperationCountForStep(s)` across the closed prefix;
5. the stored terminal semantic digest equals the recovered history/evidence accumulator at that cut.

Snapshot physical representation MAY stream the compact certificate; it MUST NOT expand the full historical generated catalog merely to serialize a Snapshot.

## 6. Complete `transition.committed.v1` semantic contract

### 6.1 Operation outcome

`OperationOutcomeWireV1` is fixed as:

```proto
message OperationOutcomeWireV1 {
  bytes operation_id = 1;       // exactly 16, non-ZERO
  uint32 terminal_status = 2;   // CoreOperationResultStatusV1 numeric value; terminal only
  string result_code = 3;       // StableToken
  optional bytes rich_result_payload = 4;
}
```

Normalized MV-DCBOR item:

```text
array [
  operation_id bytes16,
  terminal_status uint,
  result_code ASCII StableToken,
  [] | [rich_result_payload bytes]
]
```

Outcomes are ordered by the same canonical order as `applied_operation_ids`; the ids MUST match position-by-position and cardinalities MUST be equal.

### 6.2 Partition digest

`PartitionDigestWireV1` is fixed as:

```proto
message PartitionDigestWireV1 {
  string partition_id = 1;      // StableToken
  bytes resulting_digest = 2;   // exactly 32
}
```

Normalized MV-DCBOR item:

```text
array [ partition_id ASCII, resulting_digest bytes32 ]
```

The list is strict `partition_id` ASCII ascending with no duplicates and exactly covers the partition candidates committed by that transition.

### 6.3 Transition normalized payload

The normalized semantic payload for `transition.committed.v1` / `persistence.transition-committed / 1.0` is:

```text
map {
  0: effective_step uint64,
  1: resulting_step uint64,
  2: active_config_generation uint64,
  3: active_config_digest bytes32,
  4: applied_operation_ids [bytes16...],
  5: operation_outcomes [OperationOutcome...],
  6: previous_state_continuity_token bytes32,
  7: resulting_state_continuity_token bytes32,
  8: state_diagnostic_hash bytes32,
  9: partition_digests [PartitionDigest...]
}
```

The production builder MUST derive this payload from the same candidate/finalization material used by the SQLite transition transaction. A parallel hand-built evidence payload is forbidden.

Before COMMIT, persistence MUST cross-check that:

- every outcome corresponds to the exact terminal mutation applied in the transaction;
- active Config generation/digest equal the recovery head being committed;
- previous continuity equals the pre-transition recovery head;
- resulting continuity is derived from this transition record digest by the existing continuity rule;
- state diagnostic hash equals the resulting authoritative State diagnostic digest;
- partition digests equal the committed resulting partition candidate digests.

Recovery/replay MUST decode and normalize the same payload and fail closed on any disagreement.

## 7. Detail promotion decision authority

### 7.1 Record type

Every canonical workload transition emits exactly one Detail decision record, including Steps with zero promotion candidates:

```text
qa04.detail-promotion-decision.v1
payload schema: qa04.detail-promotion-decision / 1.0
```

It is appended in the same SQLite transaction immediately before `transition.committed.v1`. The transition history record therefore follows it in the hash chain and cryptographically binds the decision record through `previous_record_digest`.

### 7.2 Decision classes

Decision class numeric authority:

```text
1 = selected
2 = deferred
3 = not-yet-eligible
```

No other value is valid in version 1.

### 7.3 Normalized payload

For each transition:

```text
map {
  0: basis_step uint64,
  1: resulting_step uint64,
  2: array [
       array [
         decision_class uint,
         required_effective_step uint64,
         semantic_priority uint,
         detail_region_id bytes16,
         owner_domain_rank uint,
         trigger_id bytes16
       ], ...
     ]
}
```

The decision array uses the existing `DetailTransitionCanonicalOrderV1` key:

```text
required_effective_step ASC,
semantic_priority ASC,
detail_region_id ASC,
owner_domain_rank ASC,
trigger_id ASC
```

Each planner candidate appears exactly once as selected, deferred, or not-yet-eligible. Combining deferred and not-yet-eligible before persistence is forbidden.

The Step's selected set used for actual mutation MUST equal the `selected` subset of this record.

## 8. CrossDomainTransaction turnover binding

The canonical production run MUST initialize the existing 10,000 active transaction slots from the reference-world genesis authority and apply `Qa04CrossDomainTransactionTurnoverMaterializerV1` at every nonzero basis Step divisible by 300.

At each such Step:

- exactly one 1,000-slot cohort is committed;
- exactly 1,000 replacement active transactions are created in the same resulting State;
- active count remains exactly 10,000;
- replacement identity/material uses the existing canonical turnover implementation;
- the terminal and replacement states are persisted atomically with that Step's transition authority;
- the next Step consumes the resulting active slot set, not the genesis set.

No turnover is synthesized for a non-cadence Step.

At final `State(27001)`, the active set MUST still contain exactly 10,000 transactions and the run MUST have applied all due 300-Step turnover events through basis Step 27000.

## 9. Determinism accumulators

All accumulators below are streaming hash chains. They do not require materializing all evidence in memory.

For each accumulator, genesis is:

```text
D0 = DomainHash(<label>.genesis, array [])
```

For ordinal `n` with canonical normalized item digest `item_digest`:

```text
Dn = DomainHash(<label>.append,
  array [ D(n-1) bytes32, n uint64, item_digest bytes32 ])
```

The final `Dn` is the reported aggregate digest. Ordinals start at 1 and MUST be contiguous; a missing/duplicate append fails closed.

### 9.1 `transition_committed_digest`

Labels:

```text
mv.qa04-transition-committed.v1.genesis
mv.qa04-transition-committed.v1.append
```

One append for every workload transition, in basis-Step order `1..27000`.

`item_digest` is the `normalized_payload_digest` of that transition's canonical `transition.committed.v1` record.

Expected append count: exactly 27,000.

### 9.2 `operation_terminal_semantic_digest`

Labels:

```text
mv.qa04-operation-terminal.v1.genesis
mv.qa04-operation-terminal.v1.append
```

One append for each terminal Operation outcome, ordered first by effective/basis Step and then by the transition's canonical applied-operation order.

The normalized item is:

```text
array [
  effective_step uint64,
  operation_id bytes16,
  terminal_status uint,
  result_code ASCII StableToken,
  [] | [rich_result_payload bytes]
]
```

The final append count MUST equal the exact canonical generated Operation total for injection Steps 0..26999. For the current profile this is 136,450,000. The compact implementation MAY update the accumulator from a canonical batch loop; skipping an individual semantic item is forbidden.

### 9.3 `config_history_digest`

Labels:

```text
mv.qa04-config-history.v1.genesis
mv.qa04-config-history.v1.append
```

Append 1 is the durable Config authority active at `State(1)`:

```text
array [
  1,                         // authority kind: initial
  generation uint64,
  config_digest bytes32,
  []                         // no effective Step for initial authority
]
```

Each committed `config.changed.v1` event then appends:

```text
array [
  2,                         // authority kind: changed
  generation uint64,
  config_digest bytes32,
  [effective_step uint64]
]
```

History sequence/order is authoritative. No append is generated merely because a Step observes an unchanged Config.

### 9.4 `promotion_deferral_order_digest`

Labels:

```text
mv.qa04-promotion-deferral-order.v1.genesis
mv.qa04-promotion-deferral-order.v1.append
```

Exactly one append per workload transition, basis-Step order `1..27000`.

`item_digest` is the normalized payload digest of that Step's `qa04.detail-promotion-decision.v1` record. Empty decision arrays are therefore explicitly represented.

Expected append count: exactly 27,000.

## 10. Final Step2 evidence tuple

Each of the 12 process runs reports exactly these semantic digests:

```text
final_state_digest
transition_committed_digest
operation_terminal_semantic_digest
config_history_digest
promotion_deferral_order_digest
```

`final_state_digest` is the ordinary final `StateDiagnostic.state_digest` for `State(27001)`.

All five values MUST be exactly 32 bytes, non-ZERO, lower-case hex in JSON evidence, and exactly equal across all 12 runs.

CandidateId ordered-sequence digest remains independently required by `phase4-qa04-production-candidate-identity.md` and MUST also be equal across all 12 runs. It does not replace any of the five Step2 tuple members.

## 11. Evidence acceptance and fail-closed conditions

A run is ineligible for Step2 evidence if any of the following occurs:

- not exactly 27,000 committed transitions;
- final Step is not 27001;
- Operation closed-prefix has a hole or wrong terminal count;
- generated Operation collision or immutable-payload mismatch;
- transition history decode/cross-check failure;
- Detail decision candidate omitted, duplicated, or misclassified;
- 300-Step transaction turnover count/active-set drift;
- any accumulator ordinal gap/duplicate/count mismatch;
- Snapshot/recovery mismatch at the canonical running Snapshot cut;
- accepted Operation loss is nonzero;
- hidden solver iteration reduction is used;
- any of the five evidence digests is ZERO/missing;
- CandidateId sequence digest is ZERO/missing.

Step2 passes only when all 12 eligible process runs complete and all required semantic digests are exactly equal.

## 12. Implementation boundary

The implementation MAY use incremental caches, prepared SQLite statements, batched writes, streaming hash state, or profile-specific compact physical storage.

The implementation MUST NOT:

- change the canonical workload counts, family mix, State numbering, Detail budgets, transaction turnover cadence, or worker matrix;
- treat logs/metrics as authority;
- use worker count/run ordinal/process identity/time as semantic input;
- omit an Operation outcome from the terminal semantic accumulator;
- silently fall back to a reduced/synthetic/preflight matrix and call it Step2 evidence;
- set `releaseEvidenceCapable=true` merely because Step2 passes.

This amendment is deliberately scoped to the canonical QA-04 release-evidence workload. General persistence compaction for arbitrary worlds remains a separate concern.
